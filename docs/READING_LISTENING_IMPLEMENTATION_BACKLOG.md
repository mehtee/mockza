# Reading and Listening implementation backlog

Planning baseline is commit `a39349e` on 19 November 2026. This covers both Mockza (GLB) and Sanjia (IRN), including the Astro landing, React web app, and Flutter app. “Current” means present in this checkout. The public prototypes demonstrate the interaction. The production rollout and visual system are covered in the companion plan. [Web and Flutter rollout plan](WEB_FLUTTER_REDESIGN_IMPLEMENTATION_PLAN.md)

## Target learner journey

1. Finish a Reading or Listening attempt. See the saved score, missed or skipped items, and the first mistake worth reviewing.
2. Compare the submitted answer with the accepted answer. Find the exact passage text or replay the exact audio cue. See a short explanation of why the accepted answer fits and, where useful, why the selected distractor looked plausible.
3. Open a recommended exercise using new material. Reading scores the answer and the supporting line independently. Listening scores an answer from a fresh clip, then reveals the text and replays the decisive cue.
4. Use the same flow offline when the pack and media are available. Online Pro learners can request additional AI coaching grounded in the same source. Progress reports use recorded practice outcomes with visible counts.

The landing examples are a sample Reading report of **3/4** and a sample Listening report of **2/3**. Reading connects “highest demand” to “greatest demand.” Listening connects “please meet” to the updated location and “a change from” to the previous one. The two short drills grade the visitor’s selections. These are raw sample and drill counts. The app retains its existing assessment rules for calibrated results.

## First release slice

### RL-01. Normalize and validate evidence and rationale

**Owners** are content pipeline and contracts, with Web and Flutter parser changes.

- Extend the existing `ExamQuestionSchema.evidence` object with an optional typed `review` subobject and keep legacy keys readable. Continue to store it in `exam_questions.evidence_json`. Use stable `packId`, `packVersion`, `sectionId` and `questionId` as the context. Make teaching tags a small reviewed vocabulary, starting with paraphrase, unsupported inference, and revised detail. Keep the raw exam question type separately.
- Use a discriminated source reference. A passage span has a quote and a zero-based, half-open UTF-16 range in the exact canonical section `contentText`. An optional paragraph number is one-based for display. Audit the Flutter result formatter’s current paragraph increment during this migration. An audio span has `startMs` and `endMs` relative to the declared section’s media, with a transcript excerpt if verified. An omission note states which assertion the passage leaves unspecified and can identify its relevant section. All three can carry authored rationale and optional per-option notes keyed by a stable option ID or index within that same pack version.
- In legacy data, read `rationale` and `distractorNote` as authored notes when present, with `distractorExplanation` supported for existing clients and fixtures. Resolve a legacy quote by exact match within the correct section, using a verified paragraph if needed. When a quote occurs more than once or the offsets disagree, show the verified text without asserting a jump. Use existing `cueTimestampMs` plus a validated containing segment when available. A standalone cue supports a seek to a known point. Bounded replay requires a verified range.
- Start with the two pilot examples and the packs that will be featured. Audit the Listening cue outside its transcript lines, Reading quote coverage, provenance and media durations as content is added. Show untimed source text until timings are verified.
- Extend the actual publish validators. Confirm section membership, canonical text slice, range order, format, transcript and audio duration, option membership, note language, and referenced published drill. Preserve checksum and human-QA gates. Check repeated quotes, Unicode including non-BMP characters, CRLF and normalized paragraph breaks, a cue starting at zero, missing evidence, and Not Given in shared fixtures. ## AI coaching slice

### RL-06. Make the existing explainer trustworthy and useful

`POST /v1/evaluate/explain-question` already checks authentication, Pro entitlement, and a published edition-eligible question. It currently resolves the current database pack version, clears `userAnswer` before model invocation, checks the shape of generated JSON, and caches by question ID plus pack version. Grounding needs a separate check against the source. The graph prompt names IELTS and omits the authoritative full option list. An explain worker exists. The observed route invokes the graph synchronously on a cache miss. Preserve the existing endpoint and remove these ambiguities in the enhanced request path. [API route](../backend/apps/api/src/routes/evaluate.ts) · [Explainer graph](../backend/packages/ai/src/graphs/explain-question.ts) · [Explain worker](../backend/apps/worker/src/jobs/explain-question.ts) · [Cache schema](../backend/packages/db/src/schema.ts)

- Resolve skill, track, exact pack version and locale from trusted pack/section and edition policy. Supply prompt, accepted variants, option list and verified source. Use a real published source or return a typed unavailable response. Version-aware clients send the recorded version. Roll out exact matching through an additive opt-in response/request contract while older clients can still read the legacy response. Flutter currently defaults the request version in its gateway and must pass the installed attempt context before opting in.
- Ask for a short explanation of the reasoning, optional per-option notes, and source reference IDs drawn from the allowed evidence. Render the recorded selected option’s note locally. This personalizes the visible response without putting the learner’s free-text answer in a shared generation or cache. Use the answer key and scorer for exact accepted answers, including date, spelling or word-limit rules. When case-specific feedback on free text is later justified, keep any generated output and retention scoped to the learner.
- Validate both syntax and semantics after generation. Verify source IDs, text spans, audio ranges and option IDs against authoritative content. Drop or reject invented text or timestamps. Preserve literal English quotes, with explanation in the user’s supported language. Ignore instructions inside passage or answer text. Return sanitized plain text and approved references. A missing or failed explanation leaves authored evidence available.
- Namespace verified cache entries by pack ID and version or digest, question, locale/edition, and prompt-policy revision. Keep old cache data readable by old API processes during rollout. Use an additive versioned cache table if the existing primary key prevents those variants from coexisting. Prefer reviewed/prewarmed entries for highlighted content. Bound concurrent cache-miss work and coalesce identical requests. Reuse the existing worker and cache path if background generation becomes necessary.
- Carry typed explanation, note, source, and failure fields through the TypeScript gateway and Dart `Result`. Display distinct loading, offline, unavailable and Pro states without hiding the saved results. Keep stale response guards per attempt and question. Keep request/provider telemetry free of learner answers and unnecessary passage content. Retain current edition routing, quota and abuse controls.
